## 1. Cache architecture, as built

Two independent caches share this file, hardened in the same spirit but with
different mechanisms:

1. the **ASN.1 AST cache** of `parse_asn1` (`:408-649`), keyed to a
   `PROJECT_CACHE` folder (optional), which stores the *generated Python AST
   module* and the pretty-printed html — the artifact that audit finding V1
   identified as executable content;
2. the **DMT dataview cache** of `asn2dataModel` (`:782-925`), an in-process
   (`ASN2DM` dict) cache of modules generated by the DMT toolchain into a
   temp dir or an explicit `outdir`.

### 1.1 AST cache key formula

```
key = prefix + sha256(
        prefix                          # backend, also in the file name
        + str(count) + ':'              # number of input files, self-delimiting
        + Σ per-file sha256 hex digest   # in sorted-filename order (:478-484)
        + repr(key_options)
        + prefix                        # prefix again, per the code comment
      ).hexdigest()

key_options = { 'ast_version': <int>, 'rename_policy': <int>,
                'flags': <sorted ints>, 'extraflags': <list>,
                'pretty_print': <bool> }      # via _effective_options (:118-128)
```

Where it is computed: `:477-487`. `prefix` ∈ `{"", "c_", "rust_"}` derives
from `sys.argv` (`:469-474`); it is **folded into the hash and kept in the
file name** (readability; grep for `c_` entries at a glance).

Design decisions, each load-bearing:

- **Paths are deliberately NOT hashed.** The pre-fix code hashed content only
  (its commented-out path-hash was at pre-fix lines 102-117) and repaired the
  paths afterwards (`ast.asn1Files = list(*files)`, now `:486`), precisely so
  that identical ASN.1 files in different projects share one cache entry.
  This cross-project reuse is a performance requirement (TASTE/kazoo CI
  shares one cache); re-introducing paths into the key would zero the cache
  hit rate. Verified post-fix: identical content from a different project
  directory produces the same key as `tests/testsuite/test1`.
- **Options ARE hashed** (audit V3): two calls differing in
  `rename_policy`, `ast_version`, `flags`, `extraflags` or `pretty_print`
  must never share an AST. The same `key_options` object is stored in the
  manifest and re-compared verbatim on every cache hit (`:316`), so a
  manifest-key/options mismatch is also detected on disk, not only in the
  in-memory key.
- **Each file is read exactly once, in binary** (`_read_input_files`
  `:105-116`, called at `:457`), and that same content is used for (a) the
  per-input sha256 digest that feeds the key (`:481`) and (b) the digest
  recorded in the manifest — nothing else re-reads the input files.
  `file_list = sorted(list(*files))` (`:455`) fixes the iteration order so
  the key is stable regardless of the caller's ordering.
- **Count + per-file digests instead of raw content** (`:481-484`) makes
  the encoding self-delimiting: two different input *sets* can never hash
  to the same key, not even sets whose contents concatenate to the same
  bytes (e.g. `["ab", "c"]` vs `["a", "bc"]`). A plain concatenation of
  the raw contents — what the original code and the first fixed version
  used — could alias such sets (a 12-byte file hashing exactly like three
  files `"2"`/`"456"`/`"89012ab"`). The in-memory fast path (`:489-491`)
  trusts the key alone, so the encoding must be collision-free for
  *correctness*, not just for security.

### 1.2 File layout of a cache entry

An entry is a *triple* named `{prefix}{sha256hex}` in the `PROJECT_CACHE`
folder (or, when no cache folder is configured, in a
`tempfile.TemporaryDirectory(prefix='OG_ASN1SCC_')` — `:494-496` — which is
discarded when the function returns, pre-existing behaviour, kept: the
module object outlives the folder). Only cache-folder entries persist:

```
{prefix}{sha256}.py          the ASN.1 AST module generated by asn1scc (python.stg)
{prefix}{sha256}.html        pretty-printed types (only when pretty_print=True)
{prefix}{sha256}.manifest    JSON sidecar (see §1.3)
pretty_print_asn1.stg        asn1scc template, re-copied when pprint is used (:562-568)
```

An entry becomes *usable* only once its manifest exists (§1.6); a hit is
only ever taken on a fully verified triple. Old (pre-fix) md5-named entries
`{md5}.py` never match a sha256 key and are left on disk untouched —
harmless; they are simply never consulted.

### 1.3 Manifest JSON schema (field-by-field rationale)

The manifest (`_write_manifest` `:340-348`, written at `:617-627`) is JSON
with `indent=2` so a human can eyeball it:

```json
{
  "key_options": { "ast_version": 4, "rename_policy": 0,
                   "flags": [5], "extraflags": [],
                   "pretty_print": true },
  "tool": { "path": "/home/taste/tool-inst/share/asn1scc/asn1scc",
            "size": 39403520, "mtime": 1758193167.0 },
  "inputs": [ ["dataview-uniq.asn", "58f6..."], ... ],
  "artifacts": { "py": "a3f8...", "html": "b2d7... | null" }
}
```

| Field | Rationale |
|---|---|
| `key_options` | The effective compiler options that shaped this AST (V3). Re-compared verbatim against the current call's options (`:316`) — a hit under different options is impossible even if an attacker managed to plant a matching file name. Plain ints via `_effective_options` so `json` and `repr` are stable across processes and Python versions. |
| `tool` | Fingerprint of the exact asn1scc binary that produced the entry: absolute path, size, mtime (`_tool_fingerprint` `:130-140`). Re-compared on every hit (`:317`). Effect: an asn1scc upgrade (new binary size/mtime) invalidates the whole cache *automatically and safely* — the first run after an upgrade regenerates each entry once. Without it, a new compiler could be paired with an old AST. |
| `inputs` | `[filename, sha256(content)]` per input, in the same sorted order as the key (`:619-621`). The **hashes** are what matters (compared against the freshly computed `input_hashes`, `:322-326`); the file names are recorded for debuggability only, and are *not* compared — again so identical content from different projects hits. |
| `artifacts` | sha256 of the `.py` content and of the `.html` content (or `null` when `pretty_print` was false). This is the actual tamper-evidence (V1/V9): the bytes that are about to be `exec`'d must hash to the recorded value (`:330`, `:332-334`). |

The manifest is the only piece of an entry that carries *no* authority of its
own: it is trusted only after passing the same file-level checks as the
artifacts (ownership, mode, not a symlink — `_verify_cached_artifact`
`:188-207`), and only relative to the current call's key/options/tool — none
of which an attacker can forge without already having the user's uid.

### 1.4 Cache-hit decision procedure

`_check_cache` (`:291-338`) is the single decision function, called at
`:523-529`. It returns either `(None, py_content, html_content)` — a
verified HIT, with the already-read, already-verified bytes — or
`(reason, None, None)`. It **never raises**: every failure path is a reason
string.

Checks, in order, each on failure ⇒ reason + regenerate:

1. manifest, `.py`, and (iff `pretty_print`) `.html` each pass
   `_verify_cached_artifact` (`:178-206`): not a symlink (`:191`); on POSIX
   (`os.name == 'posix'`, `:195`), `fstat(fd).st_uid == os.getuid()`
   (`:197`) and `stat.S_IMODE(mode) & 0o022 == 0` (`:200`) — i.e. owned by
   the current user and not group/world-writable. The file is checked and
   read through **one and the same open descriptor** (`fstat` of the open
   `fd` at `:196`, content read from that same `fd` at `:194-205`), so a
   file swapped between the check and the read cannot slip through. On
   non-POSIX (Windows) the uid/mode checks are skipped, hash checks
   retained.
2. the manifest parses as UTF-8 JSON into a dict (`:309-314`);
3. `key_options` equals the current call's options exactly (`:314`);
4. `tool` equals the fingerprint of the asn1scc binary that is about to run
   (`:317`);
5. `inputs` is a list of the same length, whose recorded content-hashes
   equal the freshly computed ones (`:318-326`) — content only, never paths;
6. `artifacts.py` equals sha256 of the read `.py` bytes (`:330`); and, when
   the call asked for html, `artifacts.html` equals sha256 of the read
   `.html` bytes (`:332-334`).

On a miss, the caller logs `Not reusing the ASN.1 cache entry: {reason}`
(`:533-534`, only when a manifest existed) and the normal generation path
runs. A miss **regenerates**; it never raises, never blocks the user, and
never asks anything. The log line `No ASN.1 file in cache (or no cache
folder)` (`:521`, `:535`) is diff-locked by four testsuite expected files
(§4.4) and must remain verbatim.

The verified bytes flow straight into execution: `_import_module_from_source`
(`:380-406`, called at `:634`) compiles the *already-verified* content with
`compile()` and `exec()`s it — there is **no second read from disk** between
verification and execution, so there is no TOCTOU window on the artifact
itself.

### 1.5 Import discipline: by path, verified bytes, never `sys.path`

`parse_asn1` never touches `sys.path`. The module is created with
`importlib.util.spec_from_file_location(module_name, filepath)`
(`:388-391`), registered in `sys.modules[module_name]` **before** execution
(`:394` — so the generated code's own sibling imports resolve), then the
verified source bytes are `compile()`d and `exec()`d (`:396-397`).

Why `compile()+exec()` of verified bytes and not `spec.loader.exec_module`:
plain `exec_module` *re-reads the file from disk* and also *writes*
`__pycache__/<name>.cpython-*.pyc` next to it (verified on Python 3.13). Both
properties would re-open V1/V2:

- re-reading means the bytes that run could differ from the bytes that were
  hash-verified a moment earlier (TOCTOU);
- the `.pyc` write means a planted `__pycache__/<hash>.cpython-313.pyc` can
  be the thing that actually executes (and importlib would create it for the
  attacker's next run).

The chosen path executes the exact bytes whose sha256 matched the manifest,
and produces no `__pycache__` in the cache folder at all.

### 1.6 Generation (cache miss) — never write through a stranger's file

Generation invokes asn1scc exactly as before — a byte-identical command line,
via `QProcess` (list args, no shell) — but in a cache folder the artifacts are
never written through files that this process does not control:

1. **the stale entry is removed first** (`_remove_stale_cache_entry`,
   `:552-555`): the previous `{key}.py`, `{key}.html` and `{key}.manifest`
   are unlinked before the compiler starts. Writing through a
   foreign-owned artifact would let another user of a shared cache folder
   choose the content that is executed, and a leftover manifest would vouch
   for files that were replaced underneath it. If a file cannot be removed
   (another user's file in a sticky folder, a read-only folder), the parse
   fails with a clear `TypeError` instead of writing through it.
2. **the artifacts are pre-created 0o600** (`_precreate_cache_artifacts`,
   `:555-556`, helper `:258-288`): the `.py` (and `.html` when pprint) is
   created by *this* process, owned by the current user and not writable by
   anyone else, **before** asn1scc starts. asn1scc truncates and rewrites
   through these files (verified: same inode, mode preserved), so the
   artifact is never group/world-writable while it holds content, and the
   attacker's classic "plant a 0666 file, rewrite it during the ~1.7 s
   compile" race has nothing to grab.
3. **the generated content is read from the very descriptors this process
   created** (`_read_generated_artifact`, `:589-610`, helper `:227-256`):
   after the compiler exits, the bytes are `os.read()` from the `O_RDWR`
   descriptor that was opened in step 2 — *not* from the path. Whatever
   happened at the path during the generation (a file unlinked and replaced,
   even one recycling the same inode number, which the kernel may hand out
   after an unlink) cannot influence the bytes that are executed. The
   descriptors are closed in a `finally` (`:609-613`), whatever the outcome.
   Outside a cache folder (tempdir) — and on Windows — the generated files
   are read by path through `_verify_cached_artifact(check_mode=False)`
   (link + ownership checks only: the folder is private, so the file's
   mode may legitimately follow the umask).
4. **the manifest is written LAST** (`:617-627`), through
   `_write_file_checked` (`:351-378`) — `O_CREAT|O_EXCL|O_NOFOLLOW`, mode
   0600, uid-checked — so the crash invariant of §1.4 holds and a symbolic
   link planted at the manifest path cannot redirect the write.
5. `_harden_cache_file_perms` (`:142-157`, applied at `:630-633`) strips
   group/world **write** bits from the files this run just created — now
   including `pretty_print_asn1.stg` when pprint was used — so a permissive
   umask cannot mint a world-writable entry that the next run would then
   (correctly) distrust. It never touches existing/foreign files, and
   failures are logged, not fatal.

The same `_write_file_checked` discipline applies to the two other fixed-name
files written into shared locations: the pretty-print template
(`:562-568` — a symlink at that path is removed first, then the template is
written without following links) and, in `asn2dataModel`, the concatenated
ASN.1 file and the staleness sidecar (`:862-867`).

The manifest-last ordering of step 4 is the crash invariant: an interrupted
or failed generation (Ctrl-C, OOM, asn1scc error) can leave an orphan
`.py`/`.html`, but never a *usable entry* — the next run finds no manifest,
logs the reason, and regenerates. This is deliberately not implemented with
temp-names + `os.replace` (the audit sketch suggested it): the
`-customStg`/`-customIcdUper` invocation stays byte-identical to the pre-fix
one, so generated code cannot drift, and the safety property is equivalent.

Empty artifacts are refused (`:594-597`, `:604-607`): asn1scc returning
silently without writing a module must not lead to executing a zero-byte or
stale file.

### 1.7 `asn2dataModel` (DMT) path

`asn2dataModel` (`:782-925`) has no on-disk keyed cache; its hardening is
about process hygiene:

- **inputs validated and read once** (`:796-798`);
- **content key**: `sha256(Σ per-file digests + count + repr(outdir))`
  (`:807-812`) keys the `ASN2DM` dict — the count-and-digest encoding, like
  the AST cache key, cannot alias two different sets of inputs (a plain
  concatenation of the contents could: `["ab","c"]` vs `["a","bc"]`).
  This also fixed a pre-existing correctness bug (the old fixed
  `'og_dataview'` key made a second call with *different* inputs return
  the *first* call's dataview);
- **tempdir lifetime**: `mkdtemp` dirs are registered in
  `_ASN2DM_TEMP_DIRS` and removed at process exit via
  `atexit.register(shutil.rmtree, …, ignore_errors=True)` (`:836-839`) — not
  per-call, because the generated modules and their `*_getset.so` must stay
  usable after the call returns; an explicit `outdir` is never removed;
  `-g` uses `./debug` created `0o700` (`:833-835`) and is never registered;
- **outdir creation**: an explicit `outdir` is created `0o700`
  (`:841`), like every other folder this module creates;
- **staleness**: a sidecar `og_dataview.inputs.sha256` records the content
  key of the inputs that produced a folder (`:715-719`, checked by
  `_dataview_files_are_current` `:722-739`) — the fragile mtime/ctime
  comparison is gone;
- **generated-file checks**: each generated module is verified before it is
  executed — not a symlink, owned by the current user
  (`_verify_cached_artifact(check_mode=False)` in `_import_dataview_modules`
  `:757-760`) — so even a caller-chosen shared `outdir` cannot serve
  foreign-planted modules to a second call. (Hash-based binding like the
  manifest is *not* done here: the DMT toolchain regenerates the files on
  every content change and there is no manifest to compare against —
  accepted residual, see §2.)
- **import discipline**: the five known generated modules
  (`_DMT_MODULES` `:54`) are imported by path in dependency order
  (`_import_dataview_modules` `:742-764`) and re-registered in `sys.modules`
  (`_register_sibling_modules` `:767-770`, also on reuse `:818`) so the
  generated code's bare `import DV` / `from Stubs import …` resolve to the
  *current* folder's modules. `sys.path.insert(0, tempdir)` (`:848`, placed
  immediately before the `try:` at `:849`) puts the folder at the *front*,
  so unknown siblings in the same folder win over anything else, including
  CWD — and it is always removed in the `finally` (`:905-913`), wherever it
  sits (third-party `sys.path` mutation included). The window is one
  `asn2dataModel` call at most; nothing survives it.

## 2. Threat model

### What the hardening defends against

| Threat | Defence |
|---|---|
| **Multi-user / shared-CI cache poisoning (V1, V4)** — another user (or another CI job's uid) writes a module into a shared `PROJECT_CACHE`, or into a committed `./debug` folder | Every file of an entry must be owned by the current uid, not group/world-writable, not a symlink, and its sha256 must match a manifest that also matches the current options and the exact asn1scc binary. Any other user's file ⇒ miss + regenerate. **This holds on the miss path too** (§1.6): before a regeneration the stale entry is unlinked and the artifacts are re-created by this process at 0600, and the generated content is read back through those very descriptors — a foreign-planted or mid-generation-replaced artifact is either refused (`TypeError`) or never read at all. |
| **Mid-generation artifact replacement (V1, remediation)** — while asn1scc runs (~1.7 s window), another user of a shared cache folder unlinks and replaces `{key}.py` with a payload | The executed bytes come from the `O_RDWR` descriptor opened *before* the compiler started (§1.6 step 3): a replacement at the path — even one recycling the same inode number — cannot reach them. A same-uid attacker who rewrites through the live descriptor remains out of threat model (below). |
| **CWD shadowing (V2)** — a `{hash}.py` planted in the model's directory is imported because `sys.path` searches CWD | `sys.path` is never consulted; the module comes from a path we construct, and the bytes executed are the bytes verified. |
| **Option confusion (V3)** — two runs with different `rename_policy`/`ast_version`/`flags`/`extraflags`/`pretty_print` silently share one AST | Options are hashed into the key and re-compared from the manifest; in-memory `AST` reuse is keyed identically. |
| **Key-collision confusion (V3/V6)** — two different *sets* of input files (whose contents concatenate identically) share one AST through the in-memory fast path | The key hashes the file *count* and each file's sha256 digest (`:478-487`) — a self-delimiting encoding that cannot alias input sets. |
| **Argument injection (V5)** — an ASN.1 file name beginning with `-` is parsed as an asn1scc option (`ASNFilename` / USE clause from the model) | `_validate_input_files` rejects `-`-prefixed and nonexistent names with `TypeError` at both `parse_asn1` and `asn2dataModel` boundaries, before any tool is spawned. |
| **Stale tempdir / `sys.path` pollution (V7)** — `asn2dataModel` leaves `sys.path[0]` pointing at a tempdir, leaks tempdirs, returns a stale dataview | `finally`-guarded `sys.path` restoration; `atexit` cleanup; content-keyed `ASN2DM`; sidecar content-key staleness check; sibling modules re-registered to the current folder. |
| **Permissive cache creation (V8)** — umask leaves cache dir/files world-writable | `makedirs(mode=0o700)` on creation; write bits stripped from newly created files (including the pretty-print template); one-time warning on an existing shared-writable folder. |
| **Forged bytecode (V1 variant)** — a planted `__pycache__/<name>.pyc` executes instead of the `.py` | Verified bytes are `compile()`d/`exec()`d directly; no `.pyc` is read or written. |
| **Stale compiler pairing** — an old AST reused with a new asn1scc | `tool` fingerprint (path/size/mtime) in the manifest; mismatch ⇒ regenerate once. |
| **Symlink-redirected writes** — a symlink planted at a fixed-name path (`{key}.manifest`, `pretty_print_asn1.stg`, the DMT concat/sidecar files) redirects an open-for-write to an arbitrary file | `_write_file_checked` writes through `O_CREAT\|O_EXCL\|O_NOFOLLOW` at mode 0600 and verifies the uid of what it opened; the stg is unlinked first if it is a link (§1.6). |

### What is explicitly NOT defended (residual risk)

- **A same-uid attacker** (another process running as the same user, or
  root). Such an attacker can rewrite artifact+manifest *consistently*,
  defeating the integrity check — but they can equally edit the user's
  source files, shell config, or the opengeode install. This is out of
  scope by construction: the manifest is tamper-evidence against *other*
  users, not a keyed signature (there is no secret to key it with). Note
  the same-uid attacker *can* also rewrite through the live pre-created
  artifact descriptor during the generation window — the descriptor binding
  (§1.6) protects against *other users*, not against the user's own
  compromised processes.
- **PATH trust (V11)** — `spawn.find_executable` for `asn1scc`,
  `asn2dataModel`, `cat`, `make` trusts `PATH`. Whoever controls `PATH`
  already controls what runs. Accepted local trust assumption; partially
  compensated: the resolved asn1scc binary is fingerprinted into every
  manifest.
- **A multi-uid shared `PROJECT_CACHE` is no longer a working cache.**
  The per-file ownership checks mean each user rejects (and regenerates)
  every other user's entries: in a group-writable non-sticky folder the
  entry ping-pongs (100 % miss rate — the cache is useless but *correct*);
  in a folder with the sticky bit (e.g. under `/tmp`), the user cannot
  unlink the other user's stale artifact and the parse stops with a clear
  `TypeError` ("… cannot be replaced (it may belong to another user of a
  shared cache folder)"). **A `PROJECT_CACHE` must now be per-uid** (the
  default `~/.local/cache/...` or a per-job CI path); a shared folder only
  ever *degrades* — to regeneration or to that clear error — never to
  executing a foreign file. Migration for an existing shared cache: give
  each user their own folder (or per-uid subfolders).
- **The user pointing `PROJECT_CACHE` at an attacker-controlled directory** —
  if you set the env var to a hostile dir, you have chosen your attacker.
  The per-file checks still apply (a foreign-uid file ⇒ regenerate or
  clear `TypeError`), so this degrades to "regenerate every time" (or to a
  clear failure when the entry cannot be replaced), not "execute the
  hostile file".
- **Confidentiality of the cache content**: the folder is created `0700`,
  but existing folders keep their permissions and generated files keep the
  umask's *read* bits (typically 0644). The hardening targets integrity.
- **The html artifact's *content*** (V9): `QTextBrowser` renders it but runs
  no JavaScript; a consistent-but-crafted html could still contain links or
  misleading text. Producing a consistent pair requires the same uid (see
  above).
- **DMT modules in a caller-chosen `outdir` are link/ownership-checked but
  not hash-bound** (§1.7): the DMT toolchain has no manifest to compare
  against, so a same-user tamper between the generation and the import
  window of `asn2dataModel` is not detected. No production caller in this
  tree passes a shared `outdir`; the mkdtemp default (mode 0700, this
  process's own folder) is the safe path.
- **The `ASN.1 Parser: using cache folder None` lines in
  `tests/testsuite/test-debug/expected_c` and `test-nocif/expected_c`** are
  stale *pre-fix* fixtures (the log line has been PROJECT_CACHE-conditional
  in the pre-fix tree already — the drift predates the security work and
  is masked by those Makefiles' `|| exit 0`). Not fixed here: the fixtures
  belong to the testsuite, outside this change's file set.

## 3. Maintenance guidance

### 3.1 Bumping the cache format

If the entry format changes (new manifest field, new key inputs, new
artifact), do **not** add migration code. Instead, make old entries *miss
naturally*:

- fold a `CACHE_FORMAT_VERSION` constant into the key hash (one
  `filehash.update(str(CACHE_FORMAT_VERSION))` line next to `:478`/`:485`)
  — old entries then have different file names and are simply never found;
- and/or add the version as a manifest field that `_check_cache` compares —
  a same-name entry then fails step 2/3 of §1.4 and regenerates.

Both mechanisms are "regenerate once", self-healing, and leave no stale
trust. The 2024→2026 md5→sha256 transition was exactly this: old
`{md5}.py` files miss on name and are left in place, harmless.

### 3.2 When the asn1scc CLI changes

The invocation at `:573-575` is built by hand (`-customStgAstVersion`,
`--field-prefix`, `-customStg`, `-renamePolicy`, optional `-customIcdUper`,
then `extraflags` and the validated file list). If a new asn1scc changes an
option's semantics:

- if it changes the **AST for given options**, the `tool` fingerprint
  (size/mtime of the binary) already invalidates old entries — nothing to
  do;
- if it changes **what the options mean** (e.g. a flag value's meaning), bump
  the cache format (§3.1) so entries generated under the old meaning never
  hit;
- if a new option is added to `parse_asn1`'s signature, **add it to
  `_effective_options`** (`:118-128`) — an option that is not in
  `key_options` is invisible to both the key and the manifest check, and V3
  comes back silently.

### 3.3 Why `TypeError` must stay the exception type

`ogParser.set_global_DV` (`ogParser.py:387-394`) — the only production
caller of `parse_asn1` — catches `(ImportError, NameError)` separately and
`TypeError` specifically, converting it to
`TypeError('ASN.1 compiler failed - {}')`. Any *new* failure path in
`Asn1scc.py` (validation, unreadable input, unparseable manifest bytes,
invalid UTF-8 html, missing generated file) must therefore raise
`TypeError`, or the user sees an unhandled traceback instead of the intended
"ASN.1 compiler failed - …" error. `_validate_input_files`,
`_read_input_files`, `_tool_fingerprint`, `_write_manifest`,
`_write_file_checked`, `_remove_stale_cache_entry`,
`_precreate_cache_artifacts`, the generated-artifact verification
(`_read_generated_artifact` → `TypeError('… cannot be trusted: …')`) and the
UTF-8 html decode (`:640-646`) all follow this convention. Cache *hits* and
*misses* are not error paths — they log and regenerate; only genuinely
unworkable states raise (a cache folder that cannot safely be written to is
one of them, by design: the alternative would be executing unverified
bytes).

### 3.4 Why `sys.path` must never be used for these imports

Every pre-fix RCE needed `sys.path` (or bare-name `importlib.import_module`)
to consider an attacker-influenced directory. The rule that falls out:

- `parse_asn1`: import by path only, no `sys.path` mutation, ever;
- `asn2dataModel`: `sys.path` may hold the tempdir only inside the
  try/finally window (insert at `:848`, before the `try:` at `:849`),
  and only at position 0 (so the folder's own siblings win over everything
  else, including CWD) — never appended, never left behind;
- never `importlib.reload` a module whose files may have been replaced on
  disk: register fresh module objects instead (`_register_sibling_modules`),
  which is what fixed the stale-first-dataview bug.

One maintenance-time caveat (review finding, residual): if a future
asn1scc `python.stg` ever emits `import` statements into the generated AST
module, those statements would resolve through `sys.path` (CWD first when
opengeode is started from the project folder). Today's generated modules
contain no imports at all (verified against real artifacts); if that ever
changes, the exec of verified bytes must be given an import hook that
resolves only against the artifact's own folder — or the generated code
must be rejected when it contains `import` outside a known-safe allowlist.

### 3.5 Performance invariants (do not regress)

The cache exists for speed; these are the invariants, with their rationale:

1. **A warm on-disk hit must skip asn1scc entirely.** The only extra I/O a
   hit may do is: hashing the input files (which the key needs anyway —
   this replaces the pre-fix md5, not additional work) plus one read of the
   cached `.py` (+`.html` when pprint) for verification. asn1scc costs
   ≈1.7 s; the added work is milliseconds. Watch for the log line
   `Reusing cached ASN.1 modules from {path}` (`:531`) on warm runs, and a
   warm−cold gap ≈ the standalone asn1scc time.
2. **No input file is read more than once.** `_read_input_files` reads each
   input exactly once; its content feeds the key and the manifest hashes,
   and nothing else re-reads the inputs.
3. **No extra file reads on the hit path** beyond §1.4's one pass (manifest,
   `.py`, `.html` each read exactly once — and those same bytes are what
   gets executed/rendered).
4. **The in-memory fast path stays**: `if new_hash in AST.keys()` (`:489-491`)
   returns before any disk access; the dict is now keyed by the full
   option-aware key, so in-process reuse is also V3-safe.
5. **Cross-project hits stay possible**: never add file *paths* (or cwd,
   hostname, timestamps) to the key — only content and options (§1.1).
   The verified paths of the current project are restored on the returned
   AST after the import (`ast.asn1Files = list(*files)`, `:638`) — also on
   a cross-project hit.
6. `_tool_fingerprint` is two `stat` calls; the asn1scc-upgrade
   regeneration it causes is one-time and correct.

### 3.6 Windows compatibility

The uid/mode checks are guarded by `os.name == 'posix'` (`:147` in
`_harden_cache_file_perms`, `:162` in `_warn_if_shared_writable`, `:195` in
`_verify_cached_artifact`, `:241` in `_read_generated_artifact`);
`_precreate_cache_artifacts` and the fd-binding of §1.6 are POSIX-only
(short-circuited by the `os.name != 'posix'` return at `:274-276`) — on
Windows the generation keeps its historical behavior (no pre-creation, no
descriptor binding, path reads with hash/manifest checks only), because
there is no multi-user file-identity model to check against there. All
`os.open` flag sets use `getattr(os, 'O_NOFOLLOW'/'O_BINARY', 0)` guards.
`os.path.join` is used throughout; `QProcess` (not `subprocess`) is used for
the tools, per the module's own Windows rationale. Do not introduce
POSIX-only calls on unconditional paths.

## 4. How to re-verify

### 4.1 Environment first

The host has two copies of opengeode (editable install *and* an orphaned
`site-packages/opengeode/`); from any cwd other than the repo root the
**stale site-packages copy wins**. Run everything with the repo copy on
top, e.g.:

```
export PYTHONPATH=/home/taste/workspace/opengeode
export PATH=~/.local/bin:$PATH     # opengeode CLI; asn1scc is on PATH via tool-inst
```

(Background and alternatives — `make install` or removing the orphaned copy —
in `docs/security-fix-baseline.md` §1.1.)

### 4.2 Security/regression unit tests

```
cd tests/pytests
PYTEST_QT_API=PySide6 python3 -m pytest test_asn1scc_cache.py   # new: cache security
PYTEST_QT_API=PySide6 python3 -m pytest                          # whole set
```

`test_asn1scc_cache.py` covers: key computation and option coverage
(`rename_policy`, `ast_version`, `flags`, `extraflags`, input-set
separation), manifest writing/verification, poisoned/symlinked/666-mode
entry rejection, **generation-window attacks** (stale artifact not written
through; artifact replaced mid-generation not executed; unremovable entry
⇒ fail-safe `TypeError`), `-g`/`./debug` poisoning (V4), forged `__pycache__`
ignored, CWD-shadowing rejection, `-`-filename `TypeError`, `sys.path`
restoration, cache folder permissions. The pre-existing `test_asn1scc.py`
(asn2dataModel via `data/dv1.asn`, `data/dv2.asn`) must keep passing. The
one expected pytest error on this host is `test_qt1.py` (fixture `qtbot` —
pytest-qt not installed; pre-existing).

### 4.3 Full regression + lint

From the repo root (note: there is no root `test-c` target — run it from
`tests/testsuite`):

```
make test-parse          # expect 125 tests, 0 errors, 5 expected failures
make test-ada            # expect 125 tests, 1 error (pre-existing test-aggregation2
                        #  Makefile bug, unrelated to the cache), 0 expected failures
cd tests/testsuite && make test-c   # expect 125 tests, 0 errors

make flake8              # or: cd opengeode && flake8 Asn1scc.py
```

API); use the same compat shim as the baseline (`/tmp/flake8_compat.py`,
documented in `docs/security-fix-baseline.md` §5). Post-fix ceiling: the
count must not exceed the post-fix reference in the verification report
(baseline pre-fix was 33; the fix landed at 23, the remediation kept it at
23 — never add new issues).

### 4.4 Locked log lines (do not reword)

The testsuite diffs opengeode's stderr against `expected*` files, so these
lines are API — edit them only with a testsuite update: `No ASN.1 file in
cache (or no cache folder)` (`test-nestedpriority/expected:2`,
`test-branchcoverage/expected:30`, `test-branchcoverage2/expected:13`,
`test-simple-decision-any/expected_c:6`) and `ASN.1 Parser: using cache
folder {dir}` (`test-debug/expected_c:4-5`, `test-nocif/expected_c:4-5`).
`Reusing cached ASN.1 modules from …`, `Reusing ASN.1 model from cache`,
`Reusing DMT outputs from previous run`, `Creating cache folder …` are used
by tooling/verification greps — keep them too.

Caveat on the two `expected_c` fixtures above: the literal lines
`[INFO] ASN.1 Parser: using cache folder None` in `test-debug/expected_c`
and `test-nocif/expected_c` are **stale pre-fix fixtures** — the log line
has been emitted only when `PROJECT_CACHE` is set since before the security
work (the pre-fix tree guarded it too, and the testsuite runs without
`PROJECT_CACHE`), so a fresh run no longer prints it. The two tests only
keep passing because their Makefiles end with `|| exit 0` (Makefile:34 in
both). Regenerating those fixtures is a testsuite change, deliberately not
done in the security work (out of its file scope).

### 4.5 Cold/warm timings (the two measurements)

Reference numbers (medians of 3, wall clock; `docs/security-fix-baseline.md`
§6 — verify against the current verification report):

| Model | Cold (fresh cache) | Warm (populated) | asn1scc alone |
|---|---|---|---|
| `tests/testsuite/test1` | 2.350 s (post-fix 2.372 s) | 0.634 s (post-fix 0.648 s) | 1.683 s |
| `tests/testsuite/test-operators` | 2.321 s | 0.589 s | 1.730 s |

Recipe:

```
# cold (fresh cache dir)
PROJECT_CACHE=/tmp/ogperf/cold_test1 opengeode og.pr system_structure.pr --check   # ×3
# warm (same dir reused)
PROJECT_CACHE=/tmp/ogperf/warm_test1 opengeode og.pr system_structure.pr --check   # ×3
```

(run per model dir: `tests/testsuite/test1`, `tests/testsuite/test-operators`;
`--check` implies `pretty_print=True`, so entries carry `.py` + `.html`.)

IMPORTANT: run the suites **sequentially** — `test-ada` and `test-rust`
operate on the same test directories and `test-ada`'s `clean` rule deletes
artifacts mid-rust-run, producing spurious failures (observed: a phantom
`test-decision` failure and ~3× inflated timings in a parallel run).

Pass criteria:

- the warm runs each log exactly one `Reusing cached ASN.1 modules from …`;
- warm medians within 20% of the reference (0.634 s / 0.589 s); cold within
  20% of 2.350 s / 2.321 s;
- warm−cold gap ≈ the standalone asn1scc time (~1.7 s) — proof the hit
  path really skips the compiler;
- first cold run after an asn1scc upgrade regenerates (expected, once).

### 4.6 PoC spot-checks

The audit's PoCs (`docs/security-audit-asn1scc-cache.md`, per-finding) are
quick negative tests worth re-running after touching the cache code: plant a
poisoned `.py` (+/− forged manifest, 666 mode, symlink, forged
`__pycache__`), a CWD `{sha256}.py`, a `-`-prefixed ASN.1 file, and two
`parse_asn1` calls differing only in `rename_policy`. Each must now be
rejected/regenerated/differently-keyed, with `Not reusing the ASN.1 cache
entry: …` or `TypeError` respectively, and no payload may execute.

For the **generation window** (§1.6): replace the freshly generated `.py`
during the compile (hook `waitfor_qprocess` in a scratch script) — the
result must be either a `TypeError('… cannot be trusted: …')` (the
replacement is foreign-owned) or, for a same-uid replacement, the payload
must *still not* be the bytes executed when the ownership check is what
defends (verify the rejected-path message, and that no manifest was left
behind). The three tests
`test_generation_writes_through_own_file`,
`test_generation_rejects_replaced_artifact` and
`test_generation_failsafe_unremovable_entry` encode exactly these and are
the fastest way to re-check.
